#+TITLE: Integration — AdminEverywhere admin panel assistant
#+STARTUP: overview

* Purpose

The Owner (2026-10-31 #hq) tasked this fork with becoming the assistant
embedded in the AdminEverywhere admin panel (khaalidrafi/admineverywhere),
first deployment Freshorama. This file is the integration contract.

* Purity law — slave-agent stays general

- No client code, client branding, or client data model ever enters this
  tree. Freshorama (and any future deployment) is a *configuration*, not
  a fork point: persona, brand vocabulary and shop settings ride profile
  config (plugins.entries.* settings) on the deployment side.
- The only brand this tree carries is the product's own, generated by
  scripts/rebrand.py per FORK.org. Hand-editing either is forbidden.
- Integration happens through the generic surfaces below. If a need does
  not fit a generic surface, we widen the surface, we do not special-case
  the client.

* What slave-agent offers (all general, anchored)

- slave-acp — the ACP stdio server (acp_adapter.entry:main); Emacs
  reaches the agent through it today, a panel host can tomorrow.
  Session resume via session/list + session/load (FORK.org, R1).
- A serving mode for web panels — an OpenAI-compatible HTTP endpoint
  (streaming /v1/chat/completions) so a generic chat UI can embed the
  agent without bespoke code. Board item; ACP stays the first-class
  surface.
- plugins/shop — a read-only, config-driven REST storefront adapter
  (StorefrontAdapter ABC, plugins/shop/adapter.py): base_url, path
  layout, filter names, status vocabulary and page shape are all
  profile settings. Money never routes through a model; read-only by
  construction until an approve-before-send gate exists.
- Profile config + secret scopes — per-deployment persona and
  credentials, consumed as env var NAMES at call time, never at import.
- Org as the memory substrate — notes, memory and task state are Org
  trees a human can read and edit (FORK.org, R3).

* Guardrails (structural, not advisory)

- Read-only before any write path exists; writes need an
  approve-before-send gate first.
- Secrets travel as env var names; a value never enters chat, config
  files or logs.
- One process serves many profiles; adapters cache per (settings,
  token) so profiles never inherit each other's connections.

* Open questions (owned by the AdminEverywhere team, letter 2026-10-31)

1. Chat transport the panel UI expects (OpenAI-compatible?
   streaming? auth header?).
2. Where the agent process runs (Django-plugin subprocess / sidecar
   container / separate host) and its resource budget.
3. Identity model: per-admin-user profiles vs a service account; which
   panel REST endpoints the assistant may read, aligned with RBAC.
4. Persona/brand injection point on their side (brand.json + profile
   config), so nothing client-specific is baked here.
5. Secrets channel: which repo secrets / env names they provision.
6. Staging contact for joint testing.
