* Law (unchanged by mobile)

- Mobile is a PROFILE + bootstrap of the same packages — never a fork.
- Purity law holds: no client code or brand enters this tree; the
  client is configuration (INTEGRATION-ADMINEVERYWHERE.org).
- No order writes until the approve-before-send gate exists.
- Secrets travel as env var NAMES; a handset is a weaker keychain than
  a server — the mobile profile stores tokens in Termux/android
  keystore where available, never in plaintext config.

* Phase 1 — Termux bootstrap (shippable NOW)

The model already runs in the cloud; the agent core is orchestration
+ tools, which a modern handset carries.  Phase 1 = agent ON the
phone via Termux (f-droid), no Tauri build required:

- ~mobile/bootstrap-termux.sh~: pkg installs (python, git, clang,
  rust, libffi, openssl — binary deps build from source on aarch64
  because manylinux wheels do not apply to Termux's bionic libc),
  clone, venv, install the lean extra, compile smoke.
- What works after bootstrap: the TUI / ~slave-acp~ stdio server,
  plugins/shop read-only tools against a configured storefront, Org
  memory in the repo tree.
- Known handset constraints (disclosed, not solved by bootstrap):
  Android kills background processes — long sessions need a Termux
  wakelock (~termux-wake-lock~); battery/heat on long turns; the
  Emacs surface does not apply on the phone.

* Phase 2 — the agent inside the admin .apk (scoped, big lift)

The admin app (khaalidrafi/admineverywhere) is Tauri 2 + Svelte 5 and
already ships an Android universal .apk.  Phase 2 embeds the agent
runtime in that apk so the phone needs nothing else:

- Runtime: CPython bundled via a Rust JNI bridge plugin (Chaquopy is
  Gradle-only, so it does not drop into the Tauri build); agent code
  rides as plain Python assets, imported by the bundled interpreter.
- Dependency reality: Android has no manylinux.  Pure-Python wheels
  (py3-none-any) are fine; every C-extension dependency must be
  rebuilt against bionic or replaced by a pure-Python alternative.
  The P1–P8 bloat-removal queue (FORK.org) is the mitigation — the
  mobile profile ships only the shop/admin toolset.
- App-side requirements: foreground service + notification for
  long-lived sessions, keystore-backed secrets, loopback-only IPC to
  the panel UI (no listening socket on the LAN).
